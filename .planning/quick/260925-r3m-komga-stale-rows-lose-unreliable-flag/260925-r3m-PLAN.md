# Komga stale rows lose their unreliable flag

## What happened

A Komga library re-import on 2026-09-22 changed the book ids. 210 stored rows
now 404 on the server, so they stopped appearing in `BooksWithProgress`.

`KomgaIngestor.Sync` computes `unreliableKeys` from the current response only,
then calls `db.MarkBulkStatus`, which clears the flag on every other row of the
source. The 202 flagged migration-era books were not in the response, so they
lost their flags while keeping their 2024 completion dates. The unattended
21:41 run then wrote 309 Day One entries, 205 of them dated 2024-03-13 or
earlier, back to 2014.

`MarkBulkStatus` is correct for Audible, where every run sees the whole library
and cluster membership is genuinely recomputed. Komga returns only books that
currently hold a read status, so "absent from the response" must not mean
"no longer unreliable".

## Fix

1. `db.MarkBulkStatusBefore(db, source, cutoff)`: set `status_is_bulk` from the
   stored `status_changed_at` for every row of the source, independent of which
   books the current response carried. Returns the number flagged.
2. `KomgaIngestor.Sync` uses it instead of `MarkBulkStatus`, and reports the
   database-wide count in `KomgaResult.Unreliable`.
3. Tests: a book that disappears from the source keeps its flag; re-syncing
   after a full id change does not unflag the old cluster. Correct
   `TestKomgaSyncFlagsCompletionsBeforeCutoff`, which asserted the wholesale
   clearing as intended behaviour and so locked the bug in.
4. Re-flag the existing database, then list the Day One entries that should
   never have been written for the user to approve.

Out of scope: detecting the 103 books re-marked on 2026-09-22 (after the
cutoff). The README states earworm does not guess at migrations; moving
`komga.unreliable_before` is the user's call.
